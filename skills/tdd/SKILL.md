# Executor TDD
The approved issue and test behaviors authorize implementation. Work only in the provided issue worktree; never update the integration branch. For each behavior, write a meaningful public-interface test, run it and observe the expected failure, implement the minimum change, then run it green. Refactor while green. Expected red failures are evidence, not failed submissions.
Commit all output on the owned branch and leave a clean checkout. Return ONLY a JSON object whose top-level keys are issueId, attempt, baseCommit, submittedCommit, and tdd. Do not add validation, documentation, cleanCheckout or other extra fields; the submission schema is strict. The tdd value is: {cycles: [{behavior, red: {exitCode, log}, green: {exitCode, log}}]}. Logs must show the behavior assertion failing and passing. For work without meaningful automated behavior, use tdd: {cycles: [], exception: "specific reason no meaningful automated behavior applies"}. Do not claim missing output as success.

If a requirement is unresolved, return JSON {"kind":"needs_input","question":"specific question","recommendedAnswer":"recommended answer","affectedRequirement":"issue criterion or PRD requirement"}. Commit or retain your current work in this worktree; do not guess or change approved scope. Ralph will release capacity while the main-session user answers and resume this same bounded attempt with the answer context. If a discovered decision needs changed scope, include revisedExplanation: {text, scope, criteria} in needs_input. Ralph records the native answer, then separately presents the revised explanation for approval, regenerates accepted planning artifacts, and preserves integrated work. An answer to the question alone never approves changed scope. Technical choices within approved scope do not require another gate.

Use the approved focused behavior command for red/green cycles when the project provides one. The host command runner will execute the complete approved configuration against the merger candidate; do not duplicate that full pipeline merely to report a submission. Run any necessary local checks sequentially within the checkout because builds and package tests can share generated assets.
